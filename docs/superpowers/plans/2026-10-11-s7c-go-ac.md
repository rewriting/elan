# S7c — AC matching in the Go compiler: Implementation Plan

> Delegated tasks, verified by the controller; one whole-branch review at the end.

**Spec:** `docs/superpowers/specs/2026-10-10-s6-rust-compiler-design.md` (S6, S6c in §5; D4) and `2026-10-11-s7-go-compiler-design.md` (S7c; G3, G5).

## Global Constraints
- Branch `s7c-go-ac`. Go >= 1.24, standard library only, offline. Written for elanc-go (S7c); the Rust compiler is frozen (docs/s6-rust-status.md) and keeps refusing AC.
- Oracles: the interpreter for semantics; REM for the output format and, where the order of AC solutions is implementation-defined, as the second opinion. Every difference of order between the interpreter and REM is analysed and documented; the tests compare such results as multisets only with a written justification per program.
- AC terms print in the order the oracles print them (canonical order of printing is part of the output): find and reproduce REM's/the interpreter's printing order of AC arguments rather than the runtime's structural order (G3).
- `make check` green at every commit; `bench_parity.py` may only improve.

## Review Focus
1. Canonical form: flattening of nested AC symbols built by right-hand sides and by matching rests; neutral elements are not ELAN's (no unit): a rest with one element is that element, an empty rest makes the match fail.
2. All solutions of an AC match, each once (multiplicities: `f(x,x,y)` against `f(a,a,a)`), in a deterministic order; conditions and `where`s tried for each solution with backtracking (unlabelled rules: first solution whose conditions hold; labelled rules under `dk`: all).
3. Non-linear variables across AC and free positions; AC symbols nested in patterns (`f(g(x,y), z)` with f, g AC); AC under free symbols and free under AC; several rest variables.
4. Commutative-only symbols (infos 1) — today refused as S6c.
5. Performance: efib, propc against the spike (RESULTS.md, go-repr NOTES: weak.Make cost, GC tuning); memory constant on long AC runs.

### Task 1: Canonical form and the common AC patterns
- AC operators as nodes with the flattened, canonically ordered arguments (elanrt AC helpers, structural order), construction functions flattening and normalising (the AC rules of the operator applied to the canonical form), printing in the oracles' order.
- Matching for one AC symbol at the root with constants, distinct variables, non-linear variables and one rest variable; conditions pruned as soon as their variables are bound (spike efib/propc).
- Tests: `tests/compiler-rs/programs/ac/` dedicated programs; the bench programs propc1-3, condac*, wpatternAC1-2 (whatever this task covers) compared with REM and the interpreter (`test_ac.sh`); efib, propc from the spike.

#### Investigation: how the oracles order, print and enumerate AC terms (2026-10-11)

Run on small programs with both oracles (operators declared `e0 a b c d zz aa f g n U V F G`, in that order).

**Printing.**
- REM keeps AC terms flattened and sorted with multiplicities (`merge_sorted_term`, src/compiler/runtime/termCommon.c:578, ascending) and prints them unflattened as a right comb (`term_unflatten`, termCommon.c:266-313): `F(a,F(b,c))`, infix `a U b U c`, each element repeated by its multiplicity, never parentheses. The order is `Gterm_cmp` (termBase.c:270-383): ints by value, strings by `strcmp`, otherwise the symbol's `prec`, which is its code in the .ref file (termBase.c:61: declaration order, not alphabetical: `zz` < `aa`), then the arguments left to right; two AC terms compare their sorted lists element by element, then multiplicity, then length (a prefix first). The compiler uses the same order on its patterns (Term.java `orderedNormalForm`). So the printed form is independent of how the term was built: `u(u(c,b),a)` and `u(a,u(b,c))` both print `a U b U c`.
- The interpreter has no canonical form: its terms are binary trees printed as built (`F(F(c,b),a)` stays so; `G(c,G(d,G(b,c)))` normalised by `G(x,x) => e` prints `G(G(b,d),e)`). Only the bindings produced by Eker's AC matcher (acmatcher/matcher/flatten.c) come out sorted, in the matcher's order: AC subterms < terms with arguments < constants, then symbol index, then arguments; ints in zigzag order (0, 1, -1, 2, ...). Strings under an AC symbol are a fatal error in the interpreter (`toacform`) and crash the REM compiler (`SymbolValue.cmp`).
- elanc-go prints as REM (the bench compares with REM's snapshots; the interpreter's output depends on the construction history): `rt.Compare` is `Gterm_cmp` with the .ref codes (`Symbol.Code`), AC terms print as a right comb. The order stays history-independent (G3). The tests compare with the interpreter modulo AC (`ac_canon.py`: both outputs flattened and sorted).

**Solutions of AC matching** (labelled rules under `dk`: every solution is a result).
- Both oracles give the same set, each distinct solution once (`x U y` on n distinct elements: 2^n-2; `a U y` on `a U a U b`: one; `f(x) U y` on `f(a) U f(a) U f(b)`: two), a variable never takes the empty multiset, a variable may take several elements; conditions filter the unconditional order.
- The orders differ in every multi-solution case tried. Two variables `x U y` on `a U b U c`: REM (`next_minimal_extract`, ac_tools.c:382) runs a counter over the sorted distinct elements for the first-written variable (the one with the higher multiplicity, else the smaller variable code), last element least significant, from 1 to all minus one: x = c, b, b U c, a, a U c, a U b; the interpreter (build_match.c) gives the first-written variable sub-multisets by decreasing size, each size in its matcher's lexicographic order: exactly the reverse here. One element pattern and a rest (`f(x) U y`): REM tries the subject's elements in ascending order (bipartite matcher, bgraph.c), the interpreter in another order; two element patterns: REM lexicographic over (x, y). Three variables, non-linear variables with others: REM rewrites them into `where` conditions (RewriteRule.java transformation3_1/3_2) matched by its copy of Eker's matcher, in another order again.
- Unlabelled rules with an AC symbol at the top are applied modulo an extension: the interpreter exports, after each such rule, its extension `F(E, lhs) => F(E, rhs)` (an `EVAR` in the .ref file, tried after the rule itself); REM adds an extension variable to the pattern (RewriteRule.java:1405, `addExtensionVariable`, not for `F(x,y)` nor for labelled rules). Labelled rules and AC patterns below a free symbol have no extension.
- Commutative-only operators do not exist in the language: the module grammar has only `(AC)` (parse/grammars/modgram.t:155); `infos 1` is never exported.

**What elanc-go does (Task 1).** Elements and variables are matched in REM's order where REM's order is known and simple: the element patterns, in source order (since 2026-10-14, after the AC bug hunt: in REM's ordered normal form, REM's transformation1/2 and the codes of its linearisation reproduced, `ir/ir.go` "AC operators"), each over the subject's elements in canonical order (each distinct choice once); then the AC-level variables: one variable of multiplicity m takes the rest (divided by m); two linear variables take REM's counter order (`rt.Split`); an unlabelled rule at the top of its AC operator takes the extension E as the interpreter does it (first the solutions where E is empty, i.e. the rest variable takes everything, then the others, `rt.Down`, from the largest). The tests compare results with REM byte for byte and in order, and with the interpreter modulo AC and as multisets where the oracles' orders differ (documented per program).

#### Task 2 findings: Eker's matcher, REM's transformations (2026-10-11)

**Eker's matcher.** Both oracles run the same code (src/compiler/runtime and src/interpreter/acmatcher/matcher: build_match.c, build_free.c, solve_free.c, build_pure.c, solve_pure.c, flatten.c differ only in allocation and in the name of the comparison). The order of its solutions depends only on the form of the terms it is given:
- Subject (REM: toEkerForm then ac_sort, eker_tools.c): the arguments of a free symbol in reverse order; an AC term as its distinct elements with multiplicities, sorted in descending order of eker_term_cmp: the kind of term (variable < AC < function < constant < builtin), then the symbol (REM's code; an int as its tagged word n<<1|1 compared unsigned: 0, 1, 2, ..., then the negative ints), then the arguments (as stored, so the last argument first), AC lists element by element then multiplicity.
- Pattern (REM: Term.java genTermForACMatcher, PatternCode, EkerTermInit): REM's ordered normal form (Term.cmp: values < variables by number < symbols by code, then the arguments; equal items grouped with a multiplicity), the variables numbered depth first in that order from 0, then ac_sort.
- Solving: the free part (simplify, simplify_ac) removes the constants of each AC level from the subject, groups the element patterns with the subjects of the same symbol into graphs, matched by brute-force backtracking (each pattern node over its matching subjects in order, nested problems solved recursively, bindings checked); each AC level with variables pushes a pure equation (its variables against the subjects left over: those of the graphs, in reverse order, then the others). The pure system (build_pure) takes the equations from the most recent, the variables of each in the pattern's order (descending: the highest number first), stably sorted the shared ones first then by decreasing multiplicity (qsort in build_assign: insertion sort, stable, below 7 elements on BSD/macOS, merge sort with glibc); each variable but the last takes a sub-multiset by increasing size (advance_owned), each size in the order of advance_select (the first ones of the term table first), the last one the rest (owned_last).
- Example: `where F(x, y) :=() a U b U c` gives (x, y) = (a U b, c), (a U c, b), (b U c, a), (a, b U c), (b, a U c), (c, a U b) in both oracles; three variables, an element pattern and a rest, x U x U y, AC nested in an element: the same order in both oracles on every program tried (tests/compiler-rs/programs/ac g_w2, g_wg, g_wxx, g_wnest; e1 spike pw2, pw3, pwg, pwxx), except with ints (the interpreter's flatten orders them 0, 1, -1, 2, ...: g_wint.multiset).

**REM's AC left-hand sides** (RewriteRule.java transformation, Term.java genDioMatching), per AC level without extension (a labelled rule, or an AC pattern under a free symbol); lhsArity counts the distinct items (equal items once, with a multiplicity):
- two variables: Diophantine code. list_x is the variable of higher multiplicity, else the one of smaller number. Both of multiplicity 1: list_x takes next_minimal_extract (a counter over the distinct elements, last least significant: `rt.Split`); x^n U y (n > 1): x takes next_maximal_extract (from the largest multiset down, the multiplicities divided by n: `rt.Down`), y the rest, never empty under a symbol (REM segfaults at the top of a labelled rule when y would be empty, g_x2y2.no-rem); x^n U y^m (n, m > 1): REM abstracts the variable that comes first (`x^n :=() X`), y^m takes the maximal extract, X the rest; REM gives the values undivided (wrong: g_x2y2u.no-rem, g_x3y2v.no-rem); elanc-go keeps REM's order with the right values.
- three items or more with two variables or more, or a repeated element pattern (transformation3_1 case 2): the variables and repeated items go to a where `F(x1^a1, ..., s^b) :=() X` matched by Eker's matcher, the element patterns of multiplicity 1 stay at the level with X; when every item would go, the first one in REM's order stays (F(x, y, z): F(x, X) where F(y, z) :=() X, x by the counter). REM normalises X before matching it (a no-op on a normal form; elanc-go matches the elements as they are, as the interpreter).
- REM's compiler stops on a where pattern with an AC operator whose variable is already bound (java.lang.InternalError: pattern not numbered: g_wnl, g_wapp), and its runtime on an AC pattern nested in an element of a level with two variables ("Warning [toEkerForm]: empty term !": g_inner).

**Extensions.** REM (transformation3_2) adds no extension to F(x, y); for the other unlabelled rules at the top of their AC operator with several variables it adds an extension variable that takes the counter (never empty) and abstracts the rest into a where (normalised, then Eker's matcher): REM never applies these rules to the whole term (H(x, x, y) on H(a, a, b), G(x, G(y, z)) on G(a, b, c): no rewrite; the interpreter: h(a, b), k(...)). The interpreter applies the rule, then its extension rule (EVAR). elanc-go follows the interpreter: the elements given to the variables (the core) from the largest multiset down (the first core is everything: no extension), each core matched as without extension, in REM's orders (g_ext2, g_ext3, g_extxxy; .no-rem where REM does not rewrite).

**Commutative-only, builtin sorts.** An AC operator on the library's int sort (which then has two constructors, the injection and the operator) is compiled (g_intac, REM's order: ints by value); an AC operation of a sort of native values (int with only the injection, builtinInt, bool, strings) is refused as S7d (no program of the bench has one; strings under AC make both oracles fail).

**Task 1 bug found.** A label whose rules have AC conditions was deterministic for the strategy compiler (Label.RulesDet), so repeat*(l) kept the first result of l only (g_repeat): CondAC and CondEker now make a label non-deterministic.

#### Task 4: review fixes (2026-10-11)

**Rewrite steps of conditional AC rules (review finding 1).** `[] F(n(i), F(n(j), x)) => F(n(i + j), x) if big(i) if big(j)` on `F(n(1), F(n(2), F(n(5), n(6))))`: the same result, elanc-go 24 steps, REM 42. What REM does (RewriteRule.java, generated C of the rule):
- transformation3_2 adds an extension variable to an unlabelled rule at the top of its AC operator only in its cases 1-5; F(x, t1, ..., tm) with one variable x of multiplicity 1 gets none unless x is *constrained* (a condition or where reads it: PatternInfo.constrainedVariable, BranchEvaluation.dependFrom; the right-hand side does not count). x then takes the rest: no enumeration of an extension (the interpreter's extensions after the rule give the same result, the conditions not reading x).
- The element patterns are matched by the bipartite matcher (MS_solve_rule: each assignment, the subject in canonical order, lexicographic in source order), x is the rest (substitution_build), possibly empty; then the conditions and wheres in order, **once per complete solution** (no pruning); then "Avoid an empty instance" fails before the right-hand side when x is empty. The rest is merged into the right-hand side without being normalised alone (steps_if3), but normalised when x stands elsewhere (steps_rest3).
- So the steps of a condition are counted once per solution of the whole match. elanc-go hoisted every simple condition as soon as its variables were bound (Task 1, for efib: `n1 == n2 + 1` on builtinInt, which takes no step, so the counts were equal there) and enumerated x modulo an extension (rt.Down): 24 steps; without hoisting 82.

Fix: only the conditions that take no step (non-linearity checks, ifs and local assignments of builtin operations and constructors) prune the matching; the others wait for the whole match. A rule F(x, t1, ..., tm), x read by no condition (`restTaker`, gen/ac.go), is matched as REM does it: x takes the rest, the rest may be empty during the match (the conditions are evaluated, steps counted, then the rule fails before its right-hand side), and x at the top AC level of the right-hand side is merged with the other arguments (rt.ExtendAC). REM itself stops without printing anything when the conditions hold with an empty x (`F(n(5), n(6))`: 4 steps, no result: a REM bug; elanc-go returns the term).
