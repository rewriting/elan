# S5b — Sanitising the compiler

Date: 2026-10-10 · Status: **done** (decided autonomously, user: keep
developing; macOS verification only).

Decisions and deviations found while implementing:

- Dead configuration: unifdef with the base configuration of each library
  (runtime: `COMPUTE_HCODE CSETCHP BITSET32 HASHCODE BORO BGSHARE
  NONUNDERSCORED BITSETMASK GCMEM COLOR BASETERM`; earley: its 21 `-D`
  options, ATERM included). `CSETCHP` is kept in the installed headers and
  skeletons (the generated Makefile defines it only without `-noC`).
  `DEBUG` is kept, with the `-dbg` libraries: they are linked by
  `elanc -debug` and `elanc -choicePointDebug`, which work (no bench test
  uses them; both variants are compiled with `-Werror`). The `BITSETINT`
  variant (`bitset_tab_int.c`) is removed; `bitset_tab_mask.c` is compiled
  once (through `bitset.c`).
- `-fno-common` is explicit: Apple Clang still defaults to `-fcommon`.
- The installed headers and the main skeletons (runtime code #included by
  the generated main file) compile as strict C17 with `-Wall -Wextra`; the
  C generated by REM keeps `-std=gnu89 -w -fcommon` (D3).
- Sanitizers: the compiler's libraries and the generated programs are built
  with UBSan only, also on Linux: cpl copies the C stack, which ASan's
  redzones forbid (D2 keeps cpl). elanc bakes the options in (`ELAN_SANITIZE`
  in the generated Makefile).
- `str_eval2` DC/ONE and IFTOE (strategies evaluated at run time): in 3.6 they
  crashed (an index used as a pointer); once that was fixed, `fail()`
  expanding to two statements made them fail unconditionally. They now stop
  with an explicit "not supported by the compiler" error (review finding);
  implementing them is in docs/followups.md.
- Integers print their low 32 bits (`%d` of `(int)GgetInt`), as in 3.6 and the
  interpreter (review finding: `%ld` had changed the output above 2^31;
  test `compiled_int_prints_low_32_bits`).
- REM: the mechanical `javac -Xlint` warnings of the hand-written code are
  fixed; the 325 raw-type warnings and those of the JavaCC-generated parser
  are left.

## 1. Context

S5a brought the compiler into the modern tree unchanged: REM (Java), the C
runtime (base variant), libearley (C++, with `compat/iostream.h`), cpl
(`libchoice`), built with the 2003 flags (`-std=gnu89 -w -fcommon`,
`-std=gnu++98 -fpermissive -w`). The interpreter went through the same step in
S2; S5b applies it to the compiler.

## 2. Goal and success criteria

1. The runtime, cpl and libearley compile with `-std=c17` / `-std=c++17`,
   `-Wall -Wextra -Werror`, with GCC and Clang, without `compat/` and
   without `-fcommon`/`-fpermissive` (keeping `-fsigned-char`, as the
   interpreter).
2. The code generated by REM and the runtime headers it includes compile
   cleanly with the same strictness where possible; what cannot (1990s C
   emitted by REM) is compiled with documented, narrowly scoped flags.
3. `make check-sanitize` builds the runtime and the generated programs with
   UBSan (ASan on Linux) and the J/JO tests run clean (no sanitizer report).
4. REM exits with a non-zero status on errors (missing `.ref`, parse error,
   internal exception); `javac -Xlint` warnings are reviewed (fixed where the
   fix is mechanical).
5. `make check` (Clang, GCC) and `make check-sanitize` stay 0/0; no snapshot
   changes (or documented, intended ones per CONTRIBUTING rule 4).

## 3. Decisions

| # | Decision | Reason |
|---|----------|--------|
| D1 | Same method as S2: dead configuration code removed (unifdef with the base-variant configuration), headers, strict modes, warnings by category, Clang, sanitizers; behaviour gated by the 410 J/JO snapshots at every commit. | Proven on the interpreter. |
| D2 | cpl (stack copying) is kept as is in S5b, only cleaned; a redesign (no stack copying) is a separate decision for later, needing its own tests. | Highest-risk component; its 64-bit bugs were fixed in the reference (patch 05). |
| D3 | Generated code: REM's output is not rewritten in S5b; the generated Makefile keeps `-std=gnu89 -w -fcommon` for the generated `.c` files only. | Changing the code generator is a larger project. |
