# S8 — A Go front end for ELAN and an interpreter of the compiler's IR

Date: 2026-10-11 · Status: decided by the user. The question (translated
from French): "Currently we need the interpreter to parse ELAN code and
produce the .ref. The difficulty is that the interpreter has a preprocessor
used at parse time that itself uses the interpreter, for example to build
the grammar. Could we define a parser in Go that uses the compiler for the
program pieces used during parsing?" The answer proposed and approved:
"write the S8 spec with the IR interpreter". The open questions of the
first draft were answered by the user on 2026-10-11 (§10, folded into §3,
§6 and §8).

**Names.** The user decided (S7e) that `elanc` becomes the Go compiler:
`bin/elanc` is a symlink to `elanc-go` (CMake `ELAN_ELANC=go`, the default
when Go >= 1.24 is found; `-DELAN_ELANC=rem` undoes it), REM's driver is
installed as `elanc-rem`, and `elanc-go` keeps its name. In this spec
`elanc-go` names the Go compiler under either name; "REM" is the 2004
compiler (`elanc-rem`); no test calls the bare `elanc` (S7e,
`check_rem_name.py`).

## 1. Context and decision

Since S7, `elanc-go` compiles a program from its `.ref` export, which only
the C++ interpreter can write (`elan --cexport`, decision G1). The front end
of the interpreter (lexer, macro preprocessor, module system, Earley parser
of the user's mixfix syntax, `.ref` writer) is ~10 000 lines of 1994-2003
C++. The preprocessor cannot be separated from the interpreter: a
`FOR EACH ... SUCH THAT X:=(S) t` construct (§2.2) parses `t` with the
grammar of the module being loaded, normalises it with the rules loaded so
far, applies the strategy `S`, and expands its body once per result —
operators, rules and sorts are generated from the results of a rewriting
computation.

Three ways to evaluate those fragments in Go were weighed:

* **compile them with `elanc-go`** (the literal reading of the question):
  every evaluation is a `.ref` snapshot, a generated Go module and a
  `go build` (the S7 target is under 2 s per program with a warm build
  cache); `termCommons` alone has 9 of them per instantiation (§2.3), and
  they cannot be batched, since each one changes the program the next one
  sees;
* **port the C++ rewrite engine** (`rewrite/`, `match/`, `term/`,
  `compile/`, ~13 000 lines): a third implementation of ELAN's semantics, besides the C++
  interpreter and `elanc-go`;
* **interpret the IR** of `elanc-go` (`src/compiler-go/ir`) in Go on top of
  its runtime `elanrt` (terms, sharing, AC, Eker's matcher, builtins,
  strategy combinators): the same lowering as compiled code, so the same
  semantics by construction, evaluation in microseconds, no `go build` — and
  the pieces of a Go `elan` interpreter later.

**Decision: the third.** S8 writes a Go front end that reads `.lgi`, `.spc`
and `.eln` files and produces the `.ref` model directly, evaluating the
preprocessor's fragments with a new IR interpreter (`interp`). The C++
interpreter stays the oracle until S8 is accepted, then `elanc-go` stops
needing it.

### 2.2 What the preprocessor does

`mlstream` (`lex/mlstream.cc`) sits between the lexer and the parsers and
rewrites the lexem stream:

| form | meaning | evaluates |
|---|---|---|
| module parameters | `module tuple[N,T_1,...,T_N]`: each formal is a macro whose body is the actual argument's lexems (`msemact.cc` action 188; numbers become number lexems) | nothing |
| `a_b`, `a_1` | identifiers joined by `_` (collident), then macro-expanded again (`T_I` with `I` a macro) | nothing |
| `{ ... }~N`, `X~N` | the block (lexem) repeated N times | constant expression |
| `{ ... }_I=A...B` | the block once per I = A..B, I a macro | constant expressions |
| `X_A,...,X_B` (any separator char) | `X_A , X_A+1 , ... , X_B` | constant expressions |
| constant expressions `(N-1)` | `ppexgram.t`: + - * / %, unary -, comparisons, `&`; ints only | arithmetic only |
| `FOR EACH V1:s1; V2,V3:s2 SUCH THAT V1:=(S) t AND V2:=() u ANDIF c : { body }` | for each solution of the condition list, in order, the body with each Vi a macro bound to the lexems of its value | **ELAN rewriting** |
| `IF c : { body }` | the body once if `c` normalises to true (same code path, no variables) | **ELAN rewriting** |

The evaluation of `FOR EACH` (mlstream.cc `macroexp`, `buffilex`
NEXTMATCHACTION, `rewrite/stateofexecution.cc` `isWhereBacktrackNextSol`):

1. the variables get temporary grammar rules in the current module's grammar
   (`addvarrule`, priority VARSPRI), deleted after the condition list;
2. each `t` is parsed by `actgram()->earleycall` with the grammar of the
   module being loaded (its imports, its operators declared so far, the
   macros in force), up to `:`, `AND`, `ANDIF`, `IF` or the end;
3. the strategy `S` is looked up as `S:<sort of Vi>` in the current module
   (`attach_type_mod`, `trrules.strategyindex_refs`): it must be defined by
   a module already loaded;
4. at expansion time, each condition is evaluated in turn with
   backtracking, as the `where`s of a rule: `t` instantiated, normalised
   with every unlabelled rule loaded so far (`reduce`), then `S` applied
   (`()`: the normal form only); `ANDIF c`/`IF c`: `c` normalised, kept when
   it is `true`;
5. each solution's values are written back as lexems through the printing
   form of their symbols (`term::writetobuf`: ints as number lexems,
   identifiers as identifier lexems), the body is re-read with those macros
   (so a `FOR EACH` body can contain declarations, rules, other macros, and
   nested `FOR EACH`).

### 2.4 What the `.ref` numbers depend on

`docs/ref-format.md`: a `.ref` file holds hash positions, not names, in
five tables (`tabofident` 3 000, `typet` 500, `import` 200, rule names
2 000, strategy names 500; sum of the characters modulo the size, collisions
probed by steps of 211, names truncated to 49 characters), function symbol
codes given in declaration order from 300, and the grammar rules in the
order of three dumps. To reproduce a `.ref` byte for byte, the Go front end
must:

* insert the same set of names in each table with the same collisions
  (the order of insertion matters only between names that collide); the
  tables start with the keyword lists of the MACC grammars
  (`generated/tabofident.cc`) and the builtin sorts;
* declare the same operators in the same order (imports first, depth
  first, then the module's own; `FOR EACH` bodies at their place;
  generated modules `explimpl<n>` for `any[X]` and `symbappl<n>` for
  `Symbol` imports, which the C++ writes as `.eln` files in the current
  directory, imports and deletes; spec parts; the rules the loader
  generates: `[LAB]`, `[DSTR]`, `[FSYM]`, extension rules of AC operators);
* run the export steps (`ldmain.cc` lines 1166-1192): `localize1` (rule
  names `label:sort/module!GL|LO`, the old names kept), the three grammar dumps
  with their marks, rules, strategies, query; `--cexport` differs from
  `--export` by `EVAR` (extension variables, `compile/`) and by `call`
  strategy indexes.

## 3. Goal and success criteria

1. **Same `.ref`.** `elan-go --cexport F.ref -b prog.lgi [spec.spc]` (and
   `--export`) writes a file **byte-identical** to `elan --cexport`
   (`--export`) on: the 28 `.ref` goldens (`tests/golden`: 27 bench
   programs and `call-anagram`), the 145 programs of
   `test_ref_roundtrip.sh`, every `.lgi` of `tests/compiler`,
   `tests/compiler-rs/programs` (334 `.lgi` together) and `examples/` (13),
   the 22 BenchThesis cases. A difference is allowed only
   when listed in `tests/front/differs.tsv` with its reason and the user's
   approval of that very case (S8-16: no class of differences is accepted
   in bulk, not even a C++ quirk; none is planned; the comparison of last
   resort is `ref.CompareTokens`).
2. **Same errors.** On the error corpus (the golden error programs and a new
   one, §7), the same standard error, standard output (in `-b` mode) and
   exit status as `elan -b --cexport`.
3. **No C++ needed.** `elanc-go prog[.lgi] [spec]` (and `elanc`, the same
   program after S7e) works with no `elan` on the machine (a test runs it with a `PATH` and a prefix without
   `elan`); `--front=elan` keeps the S7 path.
4. **The IR interpreter equals compiled code.** `elan-go run prog.ref`
   (the command line of a compiled program: `-noInput`, `-quiet`, query on
   stdin, the same output and exit statuses) gives the same stdout and status
   as the program built by `elanc-go` on: `test_normalise`, `test_strategies`,
   `strategy_terms`, `test_depth`, `test_query` (150 queries), the bench
   G cases and BenchThesis G (the `rewrite_step` line compared too: the
   interpreter counts what the generated code counts).
5. **Performance** (targets confirmed by the user, S8-17). Loading (front
   end and preprocessor evaluation, `.ref` written) under 0.5 s for every
   program of criterion 1 (the C++ takes 16-20 ms on the largest measured,
   §2.5) — a requirement; the IR interpreter's run times reported next to
   the C++ interpreter's and `elanc-go`'s on `bench_perf.sh`, target: not
   slower than the C++ interpreter — a miss is recorded with its figures,
   not a failure.
6. `make check` and the CI run the new tests when Go >= 1.24 is available;
   nothing in the existing chain changes; `legacy/` untouched.

## 4. Architecture

```
.lgi .spc .eln ─► lex ─► macro ─► lr ─► load ─────────────► export ─► ref.Program ─► .ref
                           │       (semantic actions;          │
                           │        terms read by earley       ├─► ir.Lower ─► gen (elanc-go)
                           │        with the module's grammar) └─► ir.Lower ─► interp (elan-go run)
                           │
                           └─ FOR EACH / IF: snapshot of load's state ─► export (on copies)
                              ─► ir.LowerQuery ─► interp ─► values as lexems ─► back into macro
```

Packages, in the module `elan` (`src/compiler-go`), standard library only:

* `front/tables`: `stringtab` (hash, probing, sizes, truncation, overflow
  errors), `mitab`, the initial contents of `tabofident`, `typet`, `import`,
  the builtin module list (modules allowed to use `code`).
* `front/lex`: the lexem encoding (shared with `elanrt/earley.Lexem`), the
  lexer (`lstream`, `lbuffer`, `ichstream` with the library lookup of
  S8-14), source positions for the messages.
* `front/macro`: the preprocessor (`mlstream`): macro table, action stack,
  the forms of §2.2, constant expressions; `FOR EACH`/`IF` call an
  evaluator interface given by `load` (S8a: an evaluator that refuses).
* `front/lr`: the LR(1) driver (`parse/grammars/include.parser`) and the
  tables of `modgram`, `ldmodgram`, `ppexgram` (S8-4).
* `front/grammar`, `front/earley`: the interpreter's grammars (composition
  of imported grammars with visibility bits, priorities, aliases, variable
  rules, generated `any`/`symbappl` module text, dumps) and its Earley
  front (S8-5).
* `front/load`: the semantic actions (`semact`, `semact3`, `ldsemact`), the
  module stack, instantiation, visibility, the symbol table (`fsymtab`), the
  rule and strategy tables (`trsystem`, `strategy`), spec parts, query,
  localisation and the export to `ref.Program`.
* `interp`: the IR interpreter (S8-7).
* `ir`: gains `LowerQuery` (S8-8); otherwise unchanged.
* `cmd/elan-go`: `elan-go [--cexport|--export F.ref] -b [options] prog.lgi
  [spec]` (the subset of `elan`'s options that matter for an export:
  `--elanlib`, `-l/--secondlib`, `--MAXLENNTERM`, `-b`) and
  `elan-go run [options] prog.ref` (S8-7, S8-15: one command, `run` a
  subcommand); `cmd/elanc-go` gains `--front` (so does `elanc`, a symlink
  to it after S7e).

## 5. Evaluating the preprocessor

**Staging.** The C++ loader is single-pass and depth-first: an `import`
loads the imported module (and its imports) completely before the next
lexem of the importer is read; the specification parts of `.spc` are turned
into modules before the `.lgi` query imports are loaded. A `FOR EACH` is
therefore evaluated against a well-defined state: every module whose loading
has ended, plus the part of the current module read so far (its operators
and rules before the `FOR EACH`; the `FOR EACH` of `termCommons` line 56
uses rules of earlier lines). The Go loader keeps that order exactly — it is
also what fixes the numbering (§2.4) — so the state is available at the same
moment.

**Evaluation** (decision S8-8):

1. the condition list is parsed by `front/earley` with the current grammar
   plus the variable rules (as the C++, rules added and deleted around it);
2. a *snapshot* of the state is exported to a `ref.Program` exactly as
   `--cexport` would export it at that point (localisation included), on
   copies: the real tables (whose insertion order is part of the numbering)
   are never touched by a snapshot;
3. `ir.LowerQuery(snapshot, q)` lowers what the query `q` reaches: the
   variables and their sorts, the conditions as the `where`s of a rule
   (`x := (S) t`, `x := () t`, `if c`), backtracking included;
4. `interp` enumerates the solutions in order (the order of the C++
   `isWhereBacktrackNextSol`: the first condition's results, each one
   extended by the next conditions);
5. each solution's values are mapped back to front-end terms (`elanrt`
   symbol code → `.ref` symbol code) and written as lexems by the port of
   `term::writetobuf`; the body is expanded with them as macros.

**Caching.** A module instantiation (`termCommons[Ops,Vars]`) is loaded once
per distinct name, as in C++, so its `FOR EACH`s are evaluated once per
instantiation. Snapshots are cached by the *version* of the state (counts of
names, operators, rules and strategies): conditions read with nothing
declared in between share one snapshot. Each condition list is lowered on
its own, restricted to what it reaches (a few rules and one strategy in
every known use). If S8d measures this above criterion 5, the snapshot
becomes incremental (the tables are append-only between two snapshots).

**Divergence.** `interp` has the compiled semantics; the C++ interpreter
differs on a few constructs (traversals, which it does not run; the cases
listed in `.no-interpreter` files). None appears in a preprocessor
condition today; if one does, the front end stops with an error naming the
construct (never a silent difference).

## 6. Decisions

| # | Decision | Reason |
|---|---|---|
| S8-1 | Preprocessor fragments are evaluated by an interpreter of the IR over `elanrt` (§1). | Same semantics as compiled code, instant, reusable for a Go interpreter. |
| S8-2 | Fidelity target: the `.ref` byte for byte (criterion 1). The front end keeps the C++ tables (sizes, hash, preloaded contents) and inserts names, declares symbols and dumps grammars at the same points; it builds `ref.Program` at the end and prints it with the existing `ref` printer. | Numbers are the contract (`docs/ref-format.md`); byte equality is a simple, total oracle. |
| S8-3 | A port, not a redesign: function by function, the C++ names in comments (as `elanrt/earley`), the same limits and error texts; the internal state mirrors the C++ tables (`fsymtab`, `typet`, `import`, `trrules`, module frames). Cleaner Go structures only where the numbering cannot see them. | The behaviour that matters (numbering, ambiguity resolution, messages) is in the details. |
| S8-4 | The module text is parsed by a Go port of the LR(1) driver with the MACC tables converted to Go by a generator (`front/lr/gen`, reading the build's generated `mparser.cc`, `ldparser.cc`, `ppexparser.cc`, `tabofident.cc`); the converted tables are checked in and a test regenerates them from the build and compares. No hand-written parser. | Semantic actions fire on the same reductions and read the stream at the same points; LR syntax errors print the same "one of (...) expected"; MACC stays the single source. |
| S8-5 | One Earley algorithm: `elanrt/earley` is generalised (a lexem source interface instead of `io.Reader`, a stop predicate, variable rules, a builder for front-end terms); the interpreter-only parts (grammar composition, aliases, the interpreter's warnings) live in `front/earley`. Condition: `test_query.sh` stays byte-identical; if a difference between the two C++ parsers cannot be expressed as an option, `front/earley` forks the core. | The two C++ parsers are one algorithm (123 diff lines); one port to maintain. |
| S8-6 | Packages in the module `elan`; `elan` requires `elan/elanrt` through a local `replace` (`elanrt` stays a separate module, installed for generated programs). | `interp` and the front end need the runtime; offline builds. |
| S8-7 | `interp` interprets `ir.IR` directly: every value an `elanrt.Term` (native families are a code generation choice, ignored), decision trees walked, conditions (`CondApply`, `CondAC`, `CondEker`, choose/try) and strategies (labels, named strategies, `Strat` elements, META) as `rt.Strat` closures built once per IR, the depth guard and exit statuses of `elanrt`. The documentation of `gen` is its specification; a construct `gen` refuses, `interp` refuses with the same status 2. Symbols are registered in `elanrt`'s table once per (`.ref` code, profile), append-only, so successive snapshots share them. | Same semantics as compiled code; the existing suites are its oracle (criterion 4). |
| S8-8 | `FOR EACH`/`IF`: snapshot export + `ir.LowerQuery` + `interp` enumeration + `writetobuf` port (§5); snapshots cached per state version, each condition list lowered on its own. | Reuses the export and the lowering instead of a second path from the loader's state to the IR. |
| S8-9 | Generated modules (spec parts, `explimpl<n>`, `symbappl<n>`) are produced as text in memory and read by the same lexer and parser; no file is written in the current directory. | Same tables and numbering; no side effect (the C++ writes and deletes `explimpl*.eln` in the user's directory). |
| S8-10 | Error messages: same text, stream and exit status for every error of the error corpus; `[error] :file=F\tline=L\tpos=P` positions computed as the C++ lexer does; the first fatal error stops the load (`failexit`). Warnings (`[warning] using the 'code' option...`, Earley ambiguity warnings) on stderr as the C++. | Users and tests read them; the goldens pin some. |
| S8-11 | Oracles: `elan --cexport` and `elan -b`; C++ test harnesses linked with `elan_core` (as `tests/unit`), never changing `elan`: `elan-lextrace` (the macro-expanded lexem stream of a file, with given parameter macros, `FOR EACH` reported but not expanded) and, if the `.ref` diff is not enough to find a numbering divergence, a table-insertion trace: `#ifdef` hooks in the C++ string table (`base/stringtab.cc`, and the other tables if needed) compiled only into a test harness target, never into `elan` (allowed by the user, §10 D2). The module loading tree that `elan` prints without `-b` ("handling module m ... end of m") is the oracle of import order. | Small, precise oracles for the early stages; `elan` unchanged (the goldens prove it). |
| S8-12 | Scope: what `elan -b --export/--cexport` needs. Not in S8: interactive commands, `-d`/`-s`/`-S` dumps, `--import` of a `.ref`, the `quote` library, `-coq`/`-proofterm`, the C code generation options of `elan`. The Go interactive interpreter `elan` (queries on stdin, results as the C++) comes later, after S8: it is not in S8's scope (§10 D4). | Keeps S8 to the compiler's needs. |
| S8-13 | The C++ interpreter stays built, installed and tested, and stays in `make check` by default after S8e, as the oracle (§10 D5; unlike the Rust compiler, G7, it does not become optional); after S8d, `elanc-go` (hence `elanc`) uses the Go front end by default, `--front=elan` restores the C++ export (reversible, as the S7e switch). | No regression path; the C++ remains the oracle. |
| S8-14 | Library lookup as `ichstream`: the name as given (current directory), then `$SECONDELANLIB` (default `..`), then `$ELANLIB/share/elanlib/{common,noquote,strategy,ref}/` (exact case); `--elanlib DIR`, `-l DIR`. | Same programs load the same files. |
| S8-15 | One command `elan-go`: `elan-go [--cexport\|--export F.ref] -b ... prog.lgi [spec]` for the front end, `elan-go run [options] prog.ref` for the IR interpreter (§10 D1). | One binary to build and install; the subcommand leaves room for the later interpreter. |
| S8-16 | Every `.ref` difference from `elan` is listed in `tests/front/differs.tsv` and approved by the user case by case; no blanket acceptance, not even for a C++ quirk (§10 D3). | Byte equality stays a total oracle. |
| S8-17 | Targets: loading under 0.5 s per program (required); IR interpreter no slower than the C++ interpreter (a miss is only recorded, with its figures) (§10 D6). | Confirmed by the user. |

## 7. Tests

* `front/...` unit tests per package (tables: hash positions of known names
  against a `.ref`; lexer and macros: `elan-lextrace` streams; LR: parses
  and syntax errors; Earley: the existing `elanrt/earley` tests plus
  variable rules and stop predicates).
* `tests/front/test_front.sh PREFIX`: for each program of criterion 1,
  `elan --cexport` and `elan-go --cexport` (and `--export`) in two work
  copies, `cmp`; on a difference, the first differing table entry or rule
  by name (a small Go tool on two `ref.Program`s), so that a numbering
  divergence is reported as "identifier `foo`: 512 vs 723", not as a line
  number.
* Error corpus `tests/front/errors/`: the golden error programs run with
  `-b --cexport`, plus one program per message family: LR syntax error,
  Earley syntax error and ambiguity, unknown module, unknown sort and
  operator, preprocessor errors (undefined macro, missing `}`, `SUCH`/`THAT`
  expected, non-affected `FOR EACH` variable, undefined strategy), table
  overflows, module parameter count mismatch. Expected outputs generated by
  `elan` and checked in.
* `interp`: the scripts of `tests/compiler-rs` and `tests/compiler` take a
  runner (`ELAN_RUN="elan-go run"`) in place of building with `elanc-go`;
  `bench_parity.py` gains a kind `V` (interpreted IR), compared with G.
* `make check-front` (in `make check` when Go is available).

## 9. Risks

* **Numbering fidelity.** One name inserted at a different moment can move
  a colliding entry; one operator declared out of order shifts every later
  symbol code. Mitigations: the port follows the C++ order of side effects
  (S8-3), the by-name `.ref` diff (§7), the table-insertion trace if needed
  (S8-11); the 145 small programs of the round trip localise problems
  before the large ones.
* **Earley fidelity.** Ambiguity resolution (priorities, associativity,
  `solveconflicts`, second pass) and the interpreter-only parts (variable
  rules with VARSPRI, aliases, `$` variables) decide which term a rule
  contains. Mitigation: the `elanrt/earley` port already matches REM on 150
  queries; module rules add every left/right-hand side of the corpora as
  tests through criterion 1.
* **Semantic actions that read the stream.** About 170 action codes, some
  of which call the Earley parser or the preprocessor and change the parser
  state (`msemact.cc` is 2 252 lines of side effects). Mitigation: the LR
  tables are the C++ ones (S8-4); actions ported one by one with their code
  numbers.
* **Preprocessor corner cases.** Macros re-expanded after `_` joining,
  blank lexems, nested `FOR EACH` with the variable table offsets
  (`bvarnamesi`), macros redefined (a warning), limits (`MAXNOFMAC` 50,
  `MAXNOFVAR` 49, `MAXDEEPCONSTEXP` 10). Mitigation: `elan-lextrace` on
  every file, the error corpus, unit tests per form.
* **Two semantics of the IR.** `gen` and `interp` can drift. Mitigation:
  every suite runs both (criterion 4); a construct is added to both in the
  same commit afterwards.
* **Load performance.** A snapshot export and a lowering per `FOR EACH`
  (about 20 in MinelaComp) and large libraries. Mitigation:
  the caching of §5, lowering restricted to what the query reaches,
  measured from S8d against criterion 5.
* **Global state of `elanrt`** (symbol table, identifiers, unique table,
  counters) shared by successive snapshots in one process. Mitigation:
  append-only registration keyed by `.ref` codes (S8-7); interpreter runs in
  their own process (`elan-go run`).
* **Scope creep** toward a full interactive interpreter (commands, traces,
  dumps). Mitigation: S8-12; anything beyond the export and `elan-go run`
  needs a new decision.
